## 摘要
大型语言模型擅长代码生成，但竞赛编程暴露了一个持续存在的失败模式：现有的多智能体流水线将工作分配给通用的规划者、编码者和调试者角色，并将算法技术的选择完全委托给骨干模型。我们提出了MARS（专用LLM的多智能体中继），一个纯提示框架，其中每个智能体都是主题专家——动态规划、图、字符串、几何等——并通过检索增强生成基于算法理论语料库进行支撑。给定一个问题，检索会选择一小组相关的专家；一个启动者编写初始的C++17解决方案，随后每一轮都在沙盒中针对公共示例运行候选方案，让活跃专家保留、修复或移交草稿，并将结构化数据包转发给下一位专家。最后，一个单一的基础设施修复过程会规范化样板代码。在CodeContests测试集上，使用Gemma 4，MARS在每个任务2.3个记录的流水线阶段达到了$0.624 \pm 0.006$的通过率（比直接提示高出14.4个百分点），以低3.3倍的墙钟成本和更小的每任务token消耗方差，缩小了与CodeSIM（$0.731$）的大部分差距。源代码可在GitHub上获取：https://github.com/fckand/mars。

## Abstract
Large Language Models excel at code generation, yet competitive programming exposes a persistent failure mode: existing multi-agent pipelines distribute work over generic planner, coder, and debugger roles and delegate the choice of algorithmic technique to the backbone alone. We present MARS (Multi-Agent Relay of Specialized LLMs), a prompt-only framework in which each agent is a topic specialist---dynamic programming, graphs, strings, geometry, and so on---grounded by retrieval-augmented generation over an algorithm-theory corpus. Given a problem, retrieval selects a small team of relevant specialists; a starter writes an initial C++17 solution, and each subsequent turn runs the candidate against public examples in a sandbox, lets the active specialist keep, repair, or hand off the draft, and forwards a structured packet to the next specialist. A single infrastructure-fixer pass normalizes boilerplate at the end. On the CodeContests test split with Gemma 4, MARS reaches $0.624 \pm 0.006$ pass rate at $2.3$ recorded pipeline stages per task ($+14.4$ percentage points over direct prompting), closing most of the gap to CodeSIM ($0.731$) at $3.3{\times}$ lower wall-clock cost and substantially smaller variance in per-task token spend. The source code is available on GitHub: https://github.com/fckand/mars.

## 1. 论文的核心问题与整体含义

- **研究动机**：大型语言模型（LLM）在代码生成上表现优异，但在竞赛编程这一标准压力测试中仍存在持续失败模式——现有基于多智能体（multi-agent）的流水线普遍将智能体划分为通用的“规划者（planner）、编码者（coder）、调试者（debugger）”角色，把算法技术选择的全部责任交给底层骨干模型，缺少真正的领域知识注入与指导。
- **核心问题**：如何让多智能体系统不是“角色分工”而是“主题分工”，使每个智能体真正携带算法领域专长，并利用检索增强生成（RAG）为每个专家提供理论语料支撑，从而提升复杂竞赛题的解决能力。
- **整体含义**：该工作提出 MARS（Multi-Agent Relay of Specialized LLMs）——一种纯提示（prompt-only）框架，将每个智能体设为单一算法主题专家（如动态规划、图论、字符串、几何等），通过自组织的小型专家团队协作、迭代、交接解题方案，以较低的推理成本显著提升通过率，展示“专业化分工 + 检索支撑”在代码生成任务中的有效性和效率优势。

## 2. 论文提出的方法论

- **核心思想**：用一个共享的算法理论语料库（cp-algorithms）通过 RAG 为 11 个主题专家智能体分别提供与其标签匹配的上下文；每个智能体在团队选择时进行“自我评估”，只让匹配任务主题的少数专家进入团队；团队内以“中继（relay）”方式顺序编辑同一份共享 C++17 代码草稿。
- **关键流程**：
  1. **团队形成**：给定一道题，每个专家根据 RAG 检索的自身领域文档回答两个问题——该题是否匹配自身专长、自己能否作为“启动者”开始解题；系统通过评分选出最多 3 个专家，并用“can-start”探针确定启动者。
  2. **中继循环**：每一轮包含两次 LLM 调用——第一次生成代码草稿；草稿在沙盒中用公共示例执行；第二次调用基于执行报告进行自我检查，输出 keep_code / repair_code / no_change 之一，并生成结构化的交接信息（handoff packet），选择下一专家。
  3. **本地门控机制**：若选择修复，则修复后的代码必须能在公共示例上编译，且通过数不低于本轮草稿，否则拒绝修复并恢复草稿；该机制用可观察的执行信号而非“自信评分”来控制 keep/repair。
  4. **终止条件**：中继最多 3 个不同专家、8 步；遇到停止信号、无未用专家、步数上限或连续无进展（streak=2 时换人，streak=3 时停止）即终止。
  5. **收尾处理**：中继结束后进行代码清理；仅当检测到样板级错误（I/O 接线、头文件、整型宽度）时，调用一次“基础设施修复器（infrastructure-fixer）”进行规范化。
- **对比创新点**：不同于 stage-aligned（规划-编码-调试）分解，MARS 采用 topic-aligned 分解；也不同于现有 RAG 代码生成（检索代码/API/代码库），MARS 检索的是“算法主题理论”语料，每专家一个切片。

- **主结果**：MARS 在 Gemma 4 上的 CodeContests 通过率达 0.624 ± 0.006，每任务 2.3 个记录的流水线阶段；相比 Direct（0.480）提升 +14.4 个百分点，比 Single-RAG（0.529）提升 +9.5，比 Parallel ensemble（0.564）提升 +6.0。

## 7. 优点

- **主题对齐的专家建模**：将智能体从通用角色（planner/coder/debugger）转变为算法主题专家，使每个智能体有明确的领域知识边界，并借助 RAG 获得理论支撑，而非依赖骨干模型的隐式泛化能力。
- **执行信号进入每个环节**：公共测试运行成为每一轮循环内的反馈，以确定性执行结果（而非自我报告信心）驱动 keep/repair 决策，并配有“不倒退”的本地门控，机制透明可靠。
- **高效且可复现**：纯提示方式无需训练；显著降低墙钟成本（相对 CodeSIM 3.3×）和 token 消耗方差；代码开源，提供完整 prompt 模板和伪代码，便于复现。
- **跨骨干、跨语言泛化验证**：在三个骨干模型和两种语言上均保持规则性优势，证明方法不是针对单一模型的过拟合。
- **诚实的 baseline 适配说明**：对 CodeSIM、PairCoder 的重跑做了详细适配说明，并逐一列出其他系统无法直接比较的具体技术障碍（如 LDB 的 Python AST 依赖、LPW 的 Python print 插桩限制、MaintainCoder 的动态需求设定、Xolver 的计算量）。

## 8. 不足与局限

- **实验覆盖有限**：仅 165 道 CodeContests 任务、单一算法语料库、两种语言（C++17/Python），未在更大规模或更现代基准（如 LiveCodeBench 更大划分）上验证；更复杂语言转换需要重新设计 prompts、提取、沙盒和基础设施。
- **外部有效性限制**：Python 复用同一算法索引和语料，未验证其他语言；题目标签依赖 Codeforces 标签体系，可能影响可迁移性。
- **无法完全隔离组件贡献**：Base relay 与 MARS 之间同时改变自检、子任务跟踪和最终修复，缺少逐项消融；去 RAG 与去专家化同时发生，不能单独说明“检索”与“主题细分”各自的边际价值。
- **门控保护较弱**：本地门仅在“同一轮草稿 vs 修复版”上防止公共测试回归，不防止下一专家引入更差代码，也不覆盖隐藏测试失败；对跨专家比较没有硬约束。
- **自评估机制的潜在偏差**：专家“自我匹配”依赖 LLM 自我判断，可能产生校准误差；团队选择与排序分数设计未充分论证，也未对比更复杂的启发式路由方法。
- **算力/资源信息缺失**：未报告 GPU 类型、数量、时间或推理后端细节，不利于成本评估和复现时的资源预估。
- **最强的对比系统仍领先**：CodeSIM 和 PairCoder 通过率均高于 MARS；PairCoder 依赖专有嵌入模型，其 0.705 的结果还受约 11% 完成截断影响，说明这些对比并非完全“同等资源条件下的公平比较”。
