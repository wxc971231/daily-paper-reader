## 摘要
代码生成系统通过模型、提示词和解码设置进行每次大语言模型调用。然而，现有的优化方法通常只调整这些选择中的一部分，或对所有任务使用一种固定配置：全局优化器为所有任务搜索一种配置，路由器仅选择模型，而提示优化器则保持模型和解码设置固定。这使得它们之间的联合、特定组别交互不清楚。因此，我们研究了这些选择如何交互，并观察到提示词与解码设置相互影响，调优效果随模型而异，且最佳配置随任务难度变化。基于这些观察，我们引入了COMPAS（面向模型、提示词和解码设置的代码生成优化），这是一种难度感知方法，通过低成本模型选择和联合提示-解码搜索来学习特定组别的质量-成本前沿，然后在线将每个测试任务路由到其匹配的前沿，无需进一步搜索。在LiveCodeBench上，在匹配的搜索预算下，COMPAS将pass@1从最佳基线的45.9%提高到52.8%，同时将成本从36.57美元降至4.92美元。该方法还可迁移到SWE-bench上的仓库级代码生成，解决了76.0%的任务，而最佳基线为70.0%。代码和可复现性工件可在https://github.com/gjz78910/COMPAS获取。

## Abstract
Code generation systems make each LLM call with a model, a prompt, and decoding settings. However, existing optimization methods usually tune only part of these choices or use one fixed configuration for all tasks: global optimizers search one configuration for all tasks, routers choose only a model, and prompt optimizers keep the model and decoding settings fixed. This leaves their joint, group-specific interactions unclear. We therefore examine how these choices interact and observe that prompts and decoding settings interact, tuning effects vary by model, and the best configuration varies by task difficulty. Guided by these observations, we introduce COMPAS (Code-generation Optimization over Models, Prompts, And Decoding Settings), a difficulty-aware method that learns group-specific quality-cost fronts through low-cost model selection and joint prompt-decoding search, then routes each test task to its matching front online without further search. Under a matched search budget on LiveCodeBench, COMPAS improves pass@1 from 45.9% for the best baseline to 52.8% while reducing cost from $36.57 to $4.92. This also transfers to repository-level code generation on SWE-bench, resolving 76.0% of tasks versus 70.0% for the best baseline. Code and the reproducibility artifact are available at https://github.com/gjz78910/COMPAS.

## 1. 核心问题与整体含义（研究动机与背景）

代码生成系统在每次调用大语言模型（LLM）时，都需要选择三个关键要素：**模型、提示词（prompt）与解码设置（decoding settings，如温度、top-p、频率惩罚）**。然而，现有优化方法往往只调整其中一部分，或对所有任务使用一套固定配置：

- **全局优化器**（如 EcoTune、EcoOptiGen）为所有任务搜索单一最优配置，忽略了任务难度差异；
- **路由方法**（如 RouteLLM）只做模型选择，保持提示词与解码设置不变；
- **提示优化方法**（如 GEPA）在固定模型与解码设置前提下优化提示词。

这种方式使模型、提示词与解码设置三者的**联合、分组特异性交互**问题悬而未决——不同难度任务可能需要完全不同的配置组合，而搜索空间极大（10 个提示 × 2 个模型 × 10³ 个解码设置 × 3 个难度组可达 60,000 个候选），难以穷举。论文通过实证研究揭示了三个关键现象，并据此提出 **COMPAS** 框架，将模型、提示词与解码设置的联合搜索与任务难度感知分组相结合，在有限预算内高效构建质量-成本前沿，并在部署时将任务路由到对应组的前沿配置。

## 2. 方法论：核心思想与关键技术细节

### 2.1 核心思想
COMPAS 采用**离线优化 + 在线部署**的范式：离线阶段按任务难度分组，为每组搜索出一个帕累托前沿（质量-成本权衡）；在线阶段仅通过查表将新任务路由到对应组的配置，不做任何在线搜索。

### 2.2 三个实证观察（动机）
1. **提示与解码设置交互**：单独优化仅达 64.3%/64.9% pass@1，联合优化可达 72.2%，因此需要联合搜索而非独立调优。
2. **联合调优的效果是模型特定的**：同一调优更新使 DeepSeek-V3 从 76.3% 提升至 77.2%，却使 DeepSeek-V3.2 从 74.0% 降至 72.1%，因此应先做模型选择。
3. **最优配置随任务难度变化**：默认配置 54.1%，最佳全局配置仅 53.4%，而分组最佳配置达 62.4%，故应构建分组前沿而非全局单一配置。

### 2.3 离线搜索阶段

**难度感知分组**：按基准自带难度标签分组（LiveCodeBench 用 Elo 评分；SWE-bench 用估计修复时间），分为 Easy/Medium/Hard 三组，搜索预算按 1:2:3 分配。LiveCodeBench 还进一步按任务接口（函数式 vs 标准输入）拆分为难度-类型组合。

**阶段一：快速模型选择**：每组随机采样最多 8 个问题，在固定种子配置 (t₀, d₀) 下探测所有候选模型，按成本感知规则选出获胜模型：

\[
m^*_g = \arg\max_{m \in M} \left[ \alpha_g \cdot \text{dquality}_m + (1-\alpha_g) \cdot \text{dcost}^{-1}_m \right]
\]

其中 α_g 对 Easy/Medium/Hard 分别设为 0.2/0.5/0.8（偏向成本、均衡、偏向质量），质量与成本均做 min-max 归一化。

**阶段二：联合提示-解码调优**：固定选中模型后，采用 LLM 反思循环联合变异提示词与解码设置。每组数据 80/20 拆分搜索池与留出池；每轮从搜索池抽小批量 Mg 评估当前候选，LLM 读取压缩反思上下文（至多 10 个失败/成功范例、搜索历史、当前前沿）后提出新候选 c′。新候选需同时在 Mg 和随机留出批 Hg 上通过接受规则 Ag（不降低分数，且修复失败任务或降低成本；留出批防止过拟合搜索池）。被接受的候选替换当前候选，若不被前沿支配则加入帕累托前沿。输出为该组的质量-成本前沿 F_g。

### 2.4 在线测试阶段
难度分配器利用任务自带标签将任务匹配到组 g(x)，从前沿 F_g(x) 中按与阶段一相同的 α_g 权重选择最大化质量-成本权衡的配置：

\[
c^*(x) = \arg\max_{c \in F_{g(x)}} \left[ \alpha_{g(x)} \cdot \text{dquality}(c) + (1-\alpha_{g(x)}) \cdot \text{dcost}(c)^{-1} \right]
\]

若前沿为空则回退至粗粒度难度前沿或默认配置。整个过程是查表操作，不消耗在线搜索预算。

## 7. 方法亮点与局限性

### 7.1 亮点

- **联合搜索空间与难度感知结合**：首次在同一框架内联合优化模型、提示词与解码设置，并按任务难度构建多组帕累托前沿，避免“一刀切”配置导致的次优。
- **成本-质量帕累托思维**：不是追求绝对最高分数，而是提供一组可权衡的配置，在线时可按偏好选择，符合真实部署需求。
- **离线优化 + 在线查表**：将昂贵的搜索过程完全离线化，在线阶段零搜索开销，使小预算用户也能受益。
- **强正则化搜索**：通过“搜索池 + 留出池”双重验证与接受规则、历史压缩反思、LLM 引导变异，在 1M token 内即完成高质量搜索，远优于基数法。

### 7.2 局限性

- **依赖任务难度标签**：虽然论文证明可用自动预估替代，但难度预估本身在真实开放域任务中难以准确获得，分组质量仍受此约束。
- **在线配置选择仍依赖 α 权重**：α 的设定是启发式的（0.2/0.5/0.8），不同业务场景可能需要重新标定，而论文未提供自适应 α 的方案。
- **未报告 GPU 算力**：全文缺少模型训练或微调阶段的硬件信息，只统计 API 成本；对自部署用户而言，硬件需求与能耗难以直接从论文评估。
- **评估范围仍限于两组任务族**：虽然覆盖竞赛题与仓库级任务，但均属于 Python/code 场景，未涉及多语言、多模态或非代码生成任务，外部效度有限。
- **Devstral 族上表现不稳定**：部分对比中 COMPAS 未胜出，说明方法对模型族特性存在一定敏感性，通用性尚需更多模型验证。

## 8. 总体评价与启示

COMPAS 是一篇**实证扎实、工程完整**的代码生成配置优化工作。其核心贡献不在于提出新的模型或训练算法，而在于系统性论证了“模型、提示词、解码设置必须联合调整，且应按任务难度分组”这一观点，并提供了一套低成本、可复用的离线搜索框架。论文在实验设计上注重公平性（相同 token 预算、相同评估协议、多种统计检验）与鲁棒性（多种子、多分割、多模型族、消融与敏感性），说服力较强。

对未来工作的启示在于：配置优化正从“全局最优”走向“分组帕累托前沿”；LLM 自身既可作生成器，也可作高效的搜索/反思工具；在 API 计费模式下，token 预算而非墙钟时间是更公平的算法效率度量。若能将难度分组与配置选择进一步端到端学习，并扩展到更多任务类型，将有可能成为代码生成系统部署的标准组件。
