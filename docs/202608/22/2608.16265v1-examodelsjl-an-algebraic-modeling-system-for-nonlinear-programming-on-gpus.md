## 摘要
大规模非线性规划几乎总是表现出部分可分离和重复的结构，然而大多数现有的代数建模系统并未利用这一点。非线性优化求解器在每次迭代时都会查询目标函数、约束条件及其导数，因此这些评估的速度直接影响到整体求解时间。我们提出了ExaModels.jl，这是一个基于Julia的代数建模系统，利用这种结构并行评估目标函数、约束条件及其导数。其核心是单指令多数据（SIMD）抽象，将非线性规划表示为少量代数模式，每个模式在许多数据点上重复。由于这些模式在编译时可见，因此为每个模式编译专门的模型和导数评估内核。将这一内核独立地应用于各个数据点，自然地映射到GPU并行性上，并且在线程足够多的情况下，无论数据点数量多少，都能实现O(1)的评估时间。在Luksan-Vlcek库的最大实例上，GPU执行相比单线程CPU评估，将稀疏Hessian评估加速了76倍；在COPS上加速了30倍，在PGLIB-OPF上加速了7.3倍。

## Abstract
Large-scale nonlinear programs almost always exhibit partially separable and repetitive structure, yet most existing algebraic modeling systems do not take advantage of it. A nonlinear optimization solver queries the objective, the constraints, and their derivatives at every iteration, so the speed of these evaluations bears directly on the overall solution time. We present ExaModels.jl, a Julia-based algebraic modeling system that exploits this structure to evaluate the objective, the constraints, and their derivatives in parallel. At its core is a single-instruction, multiple-data abstraction that represents a nonlinear program as a small number of algebraic patterns, each repeated over many data points. Because the patterns are visible at compile time, a specialized model and derivative evaluation kernel is compiled for each pattern. Applying that kernel independently across the data points maps naturally onto GPU parallelism and, with sufficiently many threads, yields O(1) evaluation time regardless of the number of data points. On the largest instances of the Luksan-Vlcek library, GPU execution speeds up sparse Hessian evaluation by 76x over single-threaded CPU evaluation, and by 30x on COPS and 7.3x on PGLIB-OPF.

## 1. 核心问题与整体含义

- **背景**：大规模非线性规划（NLP）在工程、统计和科学应用中普遍存在“部分可分、重复结构”——目标函数和约束由大量相同代数模式的标量项求和/堆叠而成（如 Goddard 火箭问题、ACOPF 潮流问题）。然而，现有的代数建模系统（AM S）大多不保留这种模式与数据的分离结构，而是将每个约束/目标项展开为扁平的标量表达式图，导致求值（目标、约束、梯度、Jacobian、Hessian）无法并行化，成为求解瓶颈。
- **核心问题**：如何建立一种建模抽象，能保留大规模 NLP 的“模式–数据”分离结构，并利用其实现高效的、可并行的 NLP 函数与导数评估，尤其是 GPU 上的原生加速？
- **整体含义**：论文提出 **ExaModels.jl**——一个 Julia 代数建模系统，通过 SIMD（单指令多数据）抽象将 NLP 表示为少量代数模式、每个模式在大量数据点上重复，利用编译期可见的结构生成专用评估内核，并将数据点映射到 GPU 线程，从而大幅降低 NLP 函数评估成本。其核心优势是：当设备线程充足时，评估时间理论上不随数据点数量增长（O(1) 并行深度），为 GPU-resident 非线性求解器提供了关键基础设施。

## 2. 方法论

- **核心思想：SIMD 抽象**
  - 将 NLP 形式化为 `(3)`：目标由少量模式 `f^(ℓ)` 在数据点 `p_i^(ℓ)` 上求和；约束由基础模式 `g^(m)`、增强模式 `h^(n)` 在各自数据点上堆叠。
  - 用户通过 `@add_var`、`@add_obj`、`@add_con` 等宏，以“代数模式 + 数据迭代器”的生成器语法描述模型（如 `@add_con(core, expr for i in 1:T)`），使模式与数据显式分离。
  - 每个模式被编译为**参数化表达式树**：树中变量索引、参数访问和数据结构访问均以“待解析”的符号方式存储，只有一个数据点作为参数；在运行时，同一棵树可被所有数据点实例化，无需每点复制。

- **参数化表达式树的实现**
  - 节点类型：`VarSource`/`ParameterSource`/`DataSource` 源节点、`Var`/`ParameterNode`/`DataIndexed` 索引节点、`Node1`/`Node2` 一般运算节点（操作符作为类型参数）。
  - 树完全编码在 Julia 类型系统中、无数组字段、为 bits 类型，因此编译器可为每个模式生成完全特化、无动态派发的代码，并可作为 GPU kernel 参数直接传递。
  - 支持编译期常量折叠、代数化简（如 `x^2 -> abs2(x)`、`x*1 -> x`）。

- **免着色的稀疏自动微分（AD）**
  - 采用反向模式（reverse-mode）AD，前向过程在表达式树上记录中间值及局部偏导，反向过程将伴随量从根传播到叶。
  - 与主流框架基于图着色、多次 matrix-vector product 不同，ExaModels.jl 在模型构建时通过“哨兵探针”确定每个模式的结构稀疏模式，并以**局部压缩的 COO 格式**直接写出各非零元。
  - `Compressor` 将同一表达式树内重复的叶访问合并到唯一非零位置；但跨模式、跨数据点不合并，以避免竞争写，实现无锁并行。
  - 二阶导数通过“reverse-over-reverse”获得，Hessian 仅存储下三角，符合 NLPModels.jl 约定。

- **GPU 内核生成**
  - 借助 KernelAbstractions.jl，一个 kernel 定义可编译到 NVIDIA、AMD、Intel、Apple GPU 及多线程 CPU。
  - 每个模式的表达式树编译为一个 kernel，每个数据点对应一个线程；不同数据点写入输出数组的不同区段，天然无冲突，无需原子操作。
  - CPU 实现使用 `@simd` 循环，GPU 实现将循环体作为 kernel 函数；GPU 上的梯度先写稀疏缓冲再压缩到稠密向量，目标函数先缓冲再归约，约束增强项类似。

- **扩展特性**：支持任意数值精度（Float32、Float64、Double64、BigFloat）、AOT 编译（`juliac --trim=safe`）、两阶段随机规划（TwoStageExaCore）、批处理（batch）建模、外部 oracle（`embed_oracle`）等。

## 5. 实验数量与充分性

**实验数量**：
- 174 个基准实例（54 LV + 54 COPS + 66 OPF），每个实例测量 5 个回调，在至少 5 种后端上运行，形成了庞大的时序矩阵。
- 求解级实验覆盖 Rosenbrock（N=20、2k、200k）和 PGLIB-OPF（1,354、9,241、78,478 节点）的四种配置。
- 编译时间实验：问题规模（1k–1M）和模式数（1–16）的两组扫描。
- GPU 缩放曲线（per-instance GPU scaling）：Rosenbrock 和 ACOPF 的渐进分析，并推算 kernel 启动开销。

**充分性与客观性**：
- 覆盖不同结构（简单链式、复杂 PDE、实际电力系统），规模跨 4 个数量级以上，后端覆盖四大 GPU 厂商。
- 严格采用稳态测量，排除 JIT 编译；GPU 计时协议量化了同步偏差；多线程 CPU 与 GPU 使用相同内核（公平性良好）。
- 报告了绝对时间和加速比，避免只给相对加速；每个实例的时序在附录给出，透明度高。
- 缺少与其他建模系统（如 JuMP、CasADi、Gravity）的直接端到端对比，只进行定性比较；但在同一框架内，对自身 CPU/GPU 和多后端比较充分。求解实验刻意对齐算法（LDL 因子化 vs cuDSS），以隔离硬件影响，但也可视为局限——未与最优 CPU 算法（如 LBL 因子化）对比。

## 6. 主要结论与发现

- **GPU 加速显著**：在最大 LV 实例上，稀疏 Hessian 评估相比单线程 CPU 加速达 76×；COPS 大实例为 30×；PGLIB-OPF 大实例为 7.3×。
- **O(1) 评估时间**：GPU 上回调耗时基本不随问题规模增长。例如 LV 小型/中型/大型的 Hessian 耗时分别为 26.9/28.3/35.7 μs，而 CPU 时间跨三个数量级增长。实际存在饱和边界，在 RTX PRO 6000 Blackwell 上明显看到增长。
- **模式粒度决定 GPU 开销**：一个模式一个 kernel，部分回调（如 OPF 的 `hess_coord!`）包含 16 个 kernel 启动；Jacobian 每 kernel 耗时在 665 倍网络规模下几乎不变。
- **GPU-resident 求解收益巨大**：全 GPU 配置（模型+求解器）相比全 CPU 配置，在 PGLIB-OPF 78,784 节点上求解速度提升 19.7 倍；其中模型驻留 GPU 比模型在 CPU 的配置额外提速 2.1 倍。当求解器仍在 CPU 时，单把模型放 GPU 对总求解时间几乎无益（因为函数评估占比小且数据传输开销大）。
- **编译成本与模式数相关、与数据规模无关**：模型创建+首次求值编译时间在问题大小变化 1000 倍时保持平坦（相差 <0.9%），在模式数从 1 增至 16 时增长 7.9×（CPU）和 1.21×（GPU，受固定编译栈开销掩盖）。
- **跨平台可移植性**：同一代码可无修改运行于 NVIDIA、AMD、Intel、Apple GPU，且速度接近（不同品牌显卡间速度差异相对有限）。

## 7. 优点

- **结构保持的建模抽象**：通过 SIMD 抽象和参数化表达式树，将“模式–数据”分离显式化，从建模到 AD 到 GPU kernel 全链路保留结构，解决了传统 AMS 扁平化损失并行性的问题。
- **高效率的编译期特化**：利用 Julia 的类型系统与 JIT，为每个模式编译专门的线性无支路 kernel；附录的 LLVM 代码显示仅 13 个浮点操作，接近手写最优（12 个操作），证明解释性开销被消除。
- **免着色的稀疏 AD**：基于模式级稀疏探针和局部压缩 COO，避免图着色开销，同时消除并行写冲突，适合 GPU 无原子操作并行。
- **跨平台 GPU 与多精度**：KernelAbstractions.jl 统一四种 GPU + 多线程 CPU；Float32 甚至 Double64/ BigFloat 均支持，Apple GPU 上可完全以单精度运行。
- **工程完整性强**：AOT 编译、两阶段随机规划、批处理、外部 oracle、可复现 benchmark 仓库、详细的逐步实现说明，都表明系统成熟度高。
- **实验透明与可复现**：每个运行的 Manifest.toml、硬件描述、脚本和原始结果均归档；时序协议谨慎处理同步偏差和稳态测量。

## 8. 不足与局限

- **编译开销**：每个新模式必须编译一次，无法“快速试错”大量不同结构模型；更适合成熟、重复部署的模型，而不适合快速原型设计。
- **建模限制**：用户必须按 SIMD 兼容形式书写模型；某些自然表达（如每个数据点结构不同）需要重构；数据数组需先于模式声明；数据依赖分支或嵌入式仿真代码无法表达为参数化表达式树，只能通过外部 oracle（效率不保证）。
- **适用范围受限**：如果问题模式多、每个模式数据点少，则加速效果微弱；GPU 收益需足够数据点才能体现。
- **无向量化库调用**：除外部 oracle 外，求值完全基于标量运算，无法利用 BLAS/sparse matrix-vector 等优化库，对某些模式可能是劣势。
- **实验覆盖的偏置**：benchmark 以自身上下文为主，没有对其他 AMS 作端到端求解时间对比；求解实验将 CPU 和 GPU 线性求解器算法刻意对齐（LDL vs cuDSS），但这可能使 CPU 算法并非最优选择，对 CPU 稍显保守；Apple 平台仅 Float32，与其他平台 Float64 不严格可比。
- **GPU 性能受 kernel 启动限制**：一个模式一个 kernel，多次启动导致微小但固有的下限；论文提出融合 kernel 或并发流可优化，但尚未实现。
